# Internationalization (Banger Picks)

## Locales

Supported app locales: **`en`** and **`es-MX`** only. Message catalogs: `src/messages/en.json` and `src/messages/es-MX.json`.

## Runtime language selection

| Audience | Rule |
|----------|------|
| **Signed out** | Browser language via `detectBrowserLanguage()` (`es*` → `es-MX`, else `en`). |
| **Signed in** | `users/{uid}.language` when set to `en` or `es-MX`. |
| **Signed in, field unset** | Treat as no preference: use browser language once, then **persist** it to the user doc. |

UI chrome and player-facing labels belong in both message files in the same PR when you add or change copy.

## CMS / Firestore editorial copy

Optional per-fixture fields (admin-written):

- English base: e.g. `whyItMatters`
- Spanish: same concept with `_esMX` suffix, e.g. `whyItMatters_esMX`
- Dashboard shows Spanish when locale is `es-MX` and the field is non-empty; otherwise English. **Do not** auto-translate in the client.

## Dates and numbers

Use the active locale’s Intl tag: **`en-US`** for English, **`es-MX`** for Spanish (`src/lib/locale-format.ts`). Do not hardcode `en-US` on player-facing surfaces. Do not apply English ordinal suffixes in Spanish UI. Do not change implied timezone behavior unless explicitly required.

## Do not translate

- Product name **Banger Picks** / **Banger Week**
- Club and player names from data providers
- Internal match-status codes in logic (`LIVE`, `HT`, `FT`); only **display labels** are translated via messages

## es-MX tone

Use natural Mexican Spanish in a **football register** (quiniela / partido vocabulary), not literal calques from English.

## QA

Ref QA (or release check) should verify **both** `en` and `es-MX`: settings language, match cards (dates, status labels, why-it-matters, Gaffer preview), and first login with a Spanish browser when `language` is unset.
